## Context

网站是 Vue 3 / Vite 静态应用，使用 hash 路由，由 `.github/workflows/pages.yml` 发布 GitHub Pages。`ManualLoadoutView.vue` 已支持 `d2hub-manual-loadout-v3` 的导入导出；`packages/loadout-planner` 可迁移 v1/v2 数据，但导入迁移包含默认值补齐和文本截断，不能直接等同于投稿严格校验。

`usePublicBuilds.js` 已隔离列表数据来源，但 `BuildLabView.vue`、`BuildDetailView.vue` 仍依赖编辑目录的 itemId、exoticArmorId、验证日期与机制分析。社区手动配装使用 Manifest Hash、多个词条组合和玩家备注，不具有这些编辑验证信息。

用户已接受：跳转 GitHub 完成写入；Issue 为公开数据源；作者关闭/重开控制自行下架；管理者用 `moderation:blocked` 屏蔽；第一版不做站内真删除。未经用户另行要求，不增加先审后发环节。

## Goals / Non-Goals

**Goals:**

- 完成投稿、浏览、修改原投稿、作者下架/恢复和管理员屏蔽/解除屏蔽。
- 保留全部手动配装字段，提供可信的 GitHub 作者身份与稳定链接。
- 自动校验与静态数据同步；权限敏感的写入由 GitHub 执行。
- 前端不存放 GitHub 写入密钥，访客列表不直接分页请求 GitHub API。

**Non-Goals:**

- 站内登录、私人云端数据、即时同步、点赞收藏系统、站内永久删除和管理员后台。
- 自动判断实机强度或把社区内容标记为已验证推荐。
- 创建独立投稿仓库或维护额外的数据站点。

## Decisions

### 1. 当前仓库的 Issue 和 Pages CI

使用当前公开项目仓库 `wh131462/destiny-2-knowledge-hub` 接收构筑投稿，不创建新仓库。`.github/ISSUE_TEMPLATE/build.md` 仅预置 build 标签；普通 Bug Issue 继续使用当前仓库，不禁用空白 Issue。

现有 `.github/workflows/pages.yml` 同时处理 master 推送、Issue 生命周期事件、手动运行和每日对账。每次检出默认分支当前代码，使用同一次 checkout 的校验器与 Manifest 目录生成快照，记录实际 checkout SHA。构建后只将生成的 `community-builds.json` 复制进 `web/dist/data/`，与整站作为同一 Pages artifact 发布。前端 CI 自动设置仓库为 github.repository，数据 URL 为 `./data/community-builds.json`；不需要跨仓库凭据、单独 Pages 站点或用户填写环境变量。

推送或手动运行时，独立初始化 job 使用 issues:write，仅创建缺失的 build 和 moderation:blocked 标签定义，不修改已存在的标签设置或任何 Issue 的标签。读取和构建 job 仅持有 issues:read。Issue 触发时跳过初始化 job，build/deploy 使用显式条件处理该跳过状态。所有触发方式使用同一并发组且不取消正在运行的部署，后续运行读取当前状态，避免旧部署覆盖新部署。

本地开发未配置时仍保留明确的未启用状态；可通过示例环境变量与本地快照测试。相比独立仓库，同仓库配置更少、没有跨域数据请求；代价是每次 Issue 更新触发整站 CI，普通 Issue 的事件也可能触发一次刷新，以免漏掉移除 build 或删除事件。

### 2. Issue 正文保存版本化投稿信封

正文包含可阅读说明和唯一一个约定的 JSON 数据块。数据块结构为 `schema: d2hub-community-build-v1`、`summary`、`activityIds`、`tags`、`loadout`；其中 `loadout` 为现有 v3 配装对象。名称来自 `loadout.name`；标题只是便于 GitHub 阅读。实现中为所有字段、数组、完整正文设置明确上限，并采用保守的 48 KiB UTF-8 正文上限；超限时报告问题，不截断玩家数据。

仅接收一个指定数据块，拒绝歧义块、未知版本、错误类型或超限数据。旧版配装先在编辑器迁移并供用户确认，再生成 v3 投稿。JSON 是唯一配装数据来源，块外文字不改变标签权限或作者身份。Issue 模板只预置 `build`，不预置任何管理标签。

稳定 ID 为仓库完整名称加 Issue number；保留 GitHub node ID、创建时间、更新时间以及原 Issue 链接。作者 numeric ID、login、头像来自 GitHub Issue 的 `user`，不采用用户可填写的作者声明，也不误用最后一次事件的 `sender`。

### 3. 写入由用户在 GitHub 确认

发布对话框预览生成内容，提供“复制投稿内容”和“前往 GitHub 投稿”。跳转 URL 仅带模板、短标题等小体积参数；不把完整 JSON 放入 URL。剪贴板失败时提供可手动复制的文本。跳转只说明待提交，不宣称上传成功。

社区详情提供“以此创建副本”和“修改原投稿”入口。编辑原投稿时在本地保存来源 Issue 和加载时的更新时间；导出更新内容后打开原 Issue，由 GitHub 判断编辑权限。无站内登录，因此入口说明只有作者/有权限者能修改，不能声称已认证当前访问者。若发现来源已更新，提示重新核对，不能默默合并或覆盖。

被隐藏的投稿仍可以由作者从 GitHub 复制原 JSON 到编辑器修改。关闭/恢复操作跳转原 Issue，GitHub 执行权限检查；网页不请求用户 Token。自动化不发布评论或向第三方发送消息；校验诊断写入快照的有限状态信息和 Actions 日志。

### 4. 上架条件是固定交集

`isPublic = has(build) && state === open && validation.valid && !has(moderation:blocked)`。

| 事件/操作 | 状态结果 |
| --- | --- |
| 创建合法的开启投稿 | 展示 |
| 编辑为合法内容 | 下次快照更新原记录 |
| 编辑为非法内容 | 下次快照移除旧公开内容并提供有限诊断 |
| 作者关闭 | 下次快照隐藏 |
| 作者重开 | 按完整条件重算 |
| 你添加屏蔽标签 | 隐藏，优先于开启与校验状态 |
| 你移除屏蔽标签 | 按完整条件重算，不强行开启 Issue |
| GitHub 永久删除或转移出投稿仓库 | 下次快照移除 |

GitHub 标签权限属于有 Triage 或更高权限的账号/授权应用，不是标签级 ACL。只有仓库所有者和明确授权者获得相关权限，才能达到用户希望的管理边界。同步构建 job 只需要 `issues: read`，标签 `build` 由投稿模板设置；管理标签在具体 Issue 上的增减只能人工管理。独立初始化 job 只创建缺失的标签定义。禁止自动化调用覆盖整个标签数组的接口，禁止解析正文命令以添加/移除管理标签。未来若加入自动补 `build`，只能追加此标签，不能改变管理标签。

### 5. 服务端校验与编辑器共享规则

提取编辑器的纯配装合法性校验，供浏览器和 Node 脚本复用，避免前端通过而 Actions 用另一套规则判断。投稿先严格检查原数据结构与长度，再做兼容处理，最后检查职业、子职业、技能池、装备栏位、异域数量、模组插槽/能量、神器与词条组合结构等现有规则。

发布最低完整度要求：有效名称、职业和子职业、简短玩法说明，以及至少一项装备或天赋配置；不要求所有武器、防具和可选备注都填写。允许明确的手动词条建议，但不据此宣称词条已由 Manifest 证实。Manifest 版本差异给出警告；当前目录可确定的非法配置阻止上架，校验所需目录整体缺失则本次同步失败，不把所有投稿判为非法并发布空列表。

### 6. 全量快照与同步可靠性

监听 `issues` 的 `opened`、`edited`、`closed`、`reopened`、`labeled`、`unlabeled`、`deleted`、`transferred`，并提供 `workflow_dispatch` 和每天一次的定时对账。监听器位于投稿仓库默认分支；关注所有上述事件，不因删除/移除标签后的事件载荷缺少 `build` 就跳过同步。

每次通过 REST 分页读取当前全部 Issue（包含关闭状态），排除 Pull Request；不按事件顺序累加数据库。分页失败、API 限流、身份/仓库访问失败、关键目录缺失时终止发布。单份投稿数据无效则只排除此记录，其余有效投稿仍可发布。

输出单个原子快照，包含 `schemaVersion`、`generatedAt`、`sourceRepository`、`manifestVersion`、`validatorRevision`、完整公开 `builds` 和最少的 Issue 状态信息。状态信息只包含编号、是否可用和必要的校验诊断，不包含被关闭/屏蔽/非法投稿的正文、标题、作者快照或配装；永久删除/转出的记录不保留。单快照防止列表和详情跨部署版本混用，也避免已移除记录的独立详情文件残留。

工作流使用共享并发组串行覆盖生成与部署，`cancel-in-progress: false`；后续运行重新读取当前状态，避免较旧运行在较新运行之后覆盖发布。GitHub 不保证事件、调度和 CDN 即时生效，前端显示数据更新时间和同步中说明。成功同步后将快照复制进本次全新的网站构建产物，不提交快照到 Git 历史。定时对账作为事件遗漏的补救；文档说明 GitHub 对无活动仓库定时工作流的停用规则及人工恢复方式。

### 7. 社区展示独立适配手动配装

`usePublicBuilds` 负责加载并校验快照，提供 loading、ready、error、unconfigured 状态和重试。首版使用一次加载的快照进行关键词、职业、活动筛选。刷新时验证单调的生成时间，避免倒退；失败时不把旧数据伪装成最新，不把网络错误当成零投稿。

列表条目使用统一轻量展示模型并保留 `source` 类型，社区装备预览按 Hash 解析。新增社区详情路由 `/builds/community/:issueNumber`，与既有编辑推荐详情并存。社区详情直接呈现完整手动配装，不调用需要编辑验证数据的 `validateBuild`、机制推荐或自动获取结论。

页面明确标记“社区投稿”，展示验证所用版本、警告和原 Issue 链接。复制导入保留词条组合、Hash、模组插槽、神器分配与全部备注。打开缺失/不可用详情时先完成快照读取，再展示不可用状态，不通过 GitHub API 绕过屏蔽回填原文。站内不做被隐藏正文的持久缓存；已打开页面及外部副本无法保证立即撤回。

## Risks / Trade-offs

- [GitHub 登录与网络门槛] → 提交、编辑、关闭跳转 GitHub；复制与本地导出始终可用。
- [最终一致性] → 展示快照时间、刷新和同步说明，不承诺实时上架/下架；同步失败保留上次成功部署，提示维护者修复并重跑。
- [公开 Issue 与撤回边界] → 下架/屏蔽只控制站内发布；文案不称为私密或永久擦除。永久删除后的当前快照会移除，但 GitHub、CDN 与外部下载副本不承诺同步清除。
- [恶意正文影响工作流或页面] → 固定代码来源、限长 JSON 解析、文本转义；不执行正文、不将正文插入 shell、不渲染原始 HTML、不从投稿提供的 URL 抓取资源。
- [授权协作者同样可操作标签] → 部署文档说明最小协作者权限；GitHub 标签本身无法限定为某个用户名独占。
- [全量同步成本] → 第一版适合早期社区；关注分页规模、Actions 用量和快照大小，规模增长后再评估索引拆分或托管数据库。
- [版本漂移] → 快照记录校验器和 Manifest 版本，升级依赖时在固定新版本上全量校验，保留原稿供作者修复。

## Migration Plan

1. 将投稿模板纳入当前仓库 `.github/ISSUE_TEMPLATE/`，在现有 Pages CI 中接入生命周期事件、标签初始化、快照生成和网站打包。
2. 本地运行投稿与状态测试，模拟 CI 生成同仓库快照并完成带项目路径的生产构建，确认快照与前端自动配置一致。
3. 将实现和配套目录推送到当前仓库默认分支，确认仓库启用 Issues、Actions 和 Pages（Source 为 GitHub Actions）。CI 使用内置 GITHUB_TOKEN，无需本地 gh 登录参与构建。
4. 验证首次 CI 创建缺失标签、发布真实快照，再用真实投稿验证关闭/恢复与屏蔽；未获用户授权不创建测试 Issue 或自动评论。
5. 回退时恢复上一版 Pages 工作流及站点；Issue 原稿不受影响，修复后重新同步。不要把关闭或屏蔽当作私密或永久擦除。

## Open Questions

无需新的仓库或配置决策。实际发布仍要求本地实现已推送到远端默认分支并由 CI 成功执行；本地配置完成不等于远端已部署。
