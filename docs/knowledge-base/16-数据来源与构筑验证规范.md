# 16 - 数据来源与构筑验证规范

## 1. 数据可信度

| 等级 | 含义 | 使用范围 |
|---|---|---|
| A | Bungie 官方页面、清单或补丁 | 名称、实体、官方规则、更新 |
| B | 可复现的游戏内测试 | 数值、交互、循环验证 |
| C | 稳定社区资料和交叉验证 | 暂无官方结构化描述的内容 |
| D | 编辑建议 | 玩法目标、操作难度和刷取优先级 |

任何 D 级判断都不能写成官方事实。

## 2. 单一数据源

- `content/`：所有实体、机制、构筑和获取路线。
- `packages/`：Schema、合法性、数值、推荐与获取规划。
- `web/`：只负责展示和用户交互。
- `docs/knowledge-base/15-已验证构筑手册.md`：由统一数据自动生成。

## 3. 构筑发布条件

一套构筑只有满足以下条件才能公开：

1. 职业、子职业和所有技能引用合法。
2. 异域和武器槽位合法。
3. 词条属于对应武器。
4. 五个护甲部位的模组容量不超过 10。
5. 声明的目标属性通过计算达到。
6. 核心机制引用机制数据库。
7. 提供完整操作循环。
8. 提供限制与失效条件。
9. 护甲套装、异域护甲和三把武器共五件核心装备都具有获取路线。
10. 标注 Manifest 版本、适用版本、核验日期和可信度。

## 5. 机制推导

- `mechanicIds` 是构筑声明；规则引擎还会从星相、碎片、异域装备和武器的 `mechanicIds` 推导实际机制集合。
- 只有同时满足所需机制的组合才会进入战斗档案，例如“光耀 + 削弱”或“灼烧 → 点燃”。
- 推导结果必须保留来源，页面和文档不得把推导机制写成未注明来源的事实。

## 6. 数值原则

- 不在没有可靠测试数据时展示虚假精确 DPS。
- 不将不同 Buff 和减伤直接相加。
- PvE 和 PvP 数值分开保存。
- 所有公式必须带版本号。
- 缺少当前补丁数据时展示“待复核”，而不是沿用旧数值。
